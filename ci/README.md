# CI

本目录存放**构建期与设计期的自动化检查**。它不是产品的一部分——产品是 `iocomm` 这个 C ABI 库，
当前尚未开始实现。

> **现状（2026-11-19）**：仓库处于设计阶段，**没有源码、没有构建入口、没有 CI provider 配置**。
> 本目录目前只有一项检查：AC-E6 的需求覆盖校验。`.github/workflows/` 的具体形态
> 等到 M0（骨架）产出 Cargo 工作区后**按真实的 crate 结构重写**——现在写死一份只有文档检查的
> workflow，M0 必然把它推倒。

---

## 目录结构

```
ci/
├── README.md              # 本文件：CI 的当前状态与后续阶段规划
├── check-ac-e6.py         # AC-E6 检查器（唯一部分，见下）
└── ac-e6-exceptions.txt   # AC-E6 的显式豁免清单
```

后续阶段会在 `ci/` 下新增检查器与编排脚本（跨平台，不依赖 CI provider），并新建：

```
.github/workflows/ci.yml   # 编排：调用 ci/ 下的检查与各阶段的构建/测试（尚未创建）
```

**分工原则**：检查逻辑一律写成 `ci/` 下可直接运行的脚本（本地与 CI 用同一条命令），
workflow 只负责「什么时候、在哪三个平台上跑」。这样本地复现不依赖 GitHub Actions 的语法，
也不会出现「CI 上有、本地跑不了」。

## AC-E6 检查器

**运行前提**：Python **3.9+**（用到 `from __future__ import annotations` + 内建泛型注解如 `list[str]`，
以及 `TextIOWrapper.reconfigure`）。不依赖任何第三方包。CI runner 镜像选型时需满足此下限。

```bash
python ci/check-ac-e6.py          # 通过则退出码 0，失败 1，检查器自身失效 2
python ci/check-ac-e6.py -v       # 逐条列出每个 P0 FR 由哪条 AC 覆盖
```

**判据**：`docs/requirements.md` §5.3 的 AC-E6 行——「每个 P0 的 FR 至少对应一条 AC」。
覆盖关系从三张验收表里取：

| 表 | 取法 |
|---|---|
| §5.1 功能验收 | 第 4 列「覆盖」 |
| §5.2 平台验收 / §5.3 工程验收 | 判定单元格里的「覆盖 `FR-x.y`」括注 |

**为什么两处写法不同**：§5.2 / §5.3 的表格只有三列（编号 / 验收项 / 判定），没有独立的覆盖列。
AC-P5 把 `FR-7.2` 写在判定里（「通过（覆盖 FR-7.2）」）。检查器两种情况都认。

**两个安全阀**：

1. **文档结构解析不到任何 P0 FR** → 退出码 **2**，而不是报告「全部通过」。
   文档大改（换表格式、改标题层级）时宁可红，也不要静默变绿。
2. **豁免清单里的条目不是 P0 FR** → 退出码 **1**。拼错一个 id 不会悄悄豁免掉别的东西。

### 豁免清单

`ci/ac-e6-exceptions.txt` 只能登记**实现约束**类 P0 FR——即「允许怎么做」而非可观测行为、
不可从 C ABI 观测的条目（先例见 `docs/open-questions.md` D-21）。登记时该 FR 的优先级列必须
同步注明「不单独挂 AC」。

当前清单只有 `FR-6.1`（异步为原语、同步为薄壳）。**新增前请先读清单文件头的三条确认项。**

⚠️ **登记是人工闸**：脚本只核「这个 id 是不是 P0 FR」（防拼写错误），**不核它是否真是实现约束**——
把一条普通需求写进清单同样会通过。条目是否成立由清单文件头的三条确认项 + 评审把关，机器守不住。

### 验证过它真的会失败

检查器的通过本身不说明什么——一个永远返回 0 的脚本也「通过」。已用变异测试逐条确认：

| 变异 | 结果 |
|---|---|
| 从 AC-108 的覆盖列删掉 `FR-1.8` | FAIL，点名 FR-1.8，退出码 1 |
| 新增一条无人认领的 P0 FR-6.99 | FAIL，点名 FR-6.99，退出码 1 |
| 把 AC-P5 的「覆盖 FR-7.2」删掉 | FAIL，点名 FR-7.2（证明 §5.2 括注**确实**被解析） |
| 豁免清单写 `FR-6.11`（拼错） | FAIL，点名无效豁免，退出码 1 |
| 在 §5.2 的「验收项」格注入转义管道 `\|`（判定格保留「覆盖 FR-7.2」） | OK——**这是有区分度的**：不感知转义的切格会把该行切成 4 格、判定被挤到第 4 格（`split('|')` 实测得 `['AC-P5', '…各编译一次(a', 'b`)', '通过（覆盖 FR-7.2）']`），按表头 3 列取第 3 格只剩 `b`)`，FR-7.2 就会报缺失；实测 OK，说明 `split_row` 确实按未转义的 `\|` 切。**原先那句写在「覆盖列」注入是不成立的**——§5.1 有 4 列，多切一格不影响取第 4 列，切错也 OK |
| 整张 FR 表被清空 | **退出码 2**（证明不会静默通过） |
| 摘掉 AC-78 对 FR-6.1 的覆盖 | OK（豁免兜住）；**清空豁免清单后同一输入 FAIL**（证明豁免是生效路径） |
| 在 `LANG=C`（ASCII stdout）下运行 | 曾抛 `UnicodeEncodeError`，**退出码 1**——与「发现无覆盖的 FR」**撞码**，CI 会把检查器崩溃误报成需求缺 AC。**已修**：启动时把 stdout/stderr 钉到 UTF-8。修复后成功路径退出码 0、失败路径仍为 1 / 2 |
| 新增一条 `**P0**`（加粗）形态且无 AC 的 FR | 曾**静默通过**（报 `OK 73 个`）——优先级判定用的是 `startswith("P0")`，漏掉了加粗形态。已修：剥离前置强调符号后判定；现报 `FAIL FR-6.98`。**实测影响**：`FR-10.17` 的优先级单元格是 `**P0**（预算）/ arena 部分 P1`，修复前根本未被计入 P0（73 → 修复后 74） |
| AC-P5 的判定写成「**不覆盖** FR-7.2」 | 曾**静默变绿**——§5.2/§5.3 分支同时套了「任意 FR 提及」正则，比文档承诺的「覆盖 `FR-x.y` 括注」更宽。已修：只认括注且排除否定前缀；现报 `FAIL FR-7.2` |
| AC-P5 的判定写成「参照 FR-7.2 的说明」 | FAIL，点名 FR-7.2。**但这条不可证伪**：`FR-7.2` **只有 AC-P5 一条覆盖**，删掉它必然报缺失——换一个有多条覆盖的 FR（如 `FR-8.8`）同一改动会静默通过。它不构成「提到 FR ≠ 覆盖 FR」的证据 |
| 输入文件不是合法 UTF-8 | 曾以未捕获 `UnicodeDecodeError` 退出、**码 1**（与「需求缺失」撞码）。已修：单独捕获并返回 **2**；2026-11-19 复测仍为 2 |

**否定式的实际覆盖面**（2026-11-19 实测，`FR-7.2` 为对象）：`不覆盖` / `未覆盖` / `并不覆盖` / `暂不覆盖` → 判为**未覆盖**（正确）；
`无覆盖` / `不是覆盖` → 仍被当成覆盖声明（**漏**）。`check-ac-e6.py` 里的 `COVER_ANNOTATION_RE` 用的是**前缀黑名单**，不是穷举。
依赖的是一条**不成文约定：判定列不出现否定式覆盖表述**（现文档中「覆盖 FR-」只有 AC-P5 一处，故当前不触发）。
新增判定文字时请避开上述写法；要根治得把正则改成白名单（「覆盖」前只允许行首 / 标点 / 空白 / 括号）。

## 约定

- **检查器必须能本地跑**：`python ci/check-ac-e6.py` 与 CI 里是**同一条命令**。
- **失败要有名字**：报错必须点名具体条目（「FR-6.9 是 P0，但没有对应的 AC」），
  不能只说「检查失败」——否则改文档的人要自己再跑一遍才知道是哪条。
- **宁可红，不要静默绿**：解析不到预期结构时退出码 2，不当作通过。
- **本目录的脚本只读仓库，不修改仓库**。
