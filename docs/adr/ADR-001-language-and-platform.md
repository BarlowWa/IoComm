# ADR-001：语言、平台与边界

- **状态**：已接受
- **日期**：2026-10-19
- **决策者**：项目负责人
- **影响**：全部模块

---

## 背景

要开发一个**工业局域网 IO 通信库**：句柄注册、发现、终端内/终端间通信、状态监控与控制、同步+异步，**不含数据格式**。

初期曾考虑把它作为既有 C++ monorepo 的子项目，因此一度倾向 C++17。但随后明确了四点：

1. 这是一个**独立的 IO 工具库**，不受既有仓库的语言/构建约束。
2. 目标平台是 **x86_64 与 ARM64**。
3. 运行环境包括 **Windows Server 2016+** 与 **Linux（RHEL 7 / 麒麟 / 统信）**。
4. 对外只用 **C ABI**。

---

## 决策

> **Rust 核心 + 纯 C ABI，支持 x86_64 与 ARM64。**

---

## 理由

### 1. 这个库的难点正好落在 Rust 的强项上

IO 工具库的四大风险：

| 风险 | Rust 的覆盖 |
|---|---|
| **异步生命周期**（回调注册/注销、对象析构、在途操作、取消竞态） | 所有权 + 借用检查 |
| **并发状态机**（连接态、发现表、句柄表、心跳/重连） | `Send` / `Sync` 编译期保证 |
| **缓冲所有权**（跨线程传递、借用期、释放时机） | 借用检查强制澄清 |
| **不可信输入**（帧头、发现报文仍网络可达） | 默认安全 |

C++ 只能靠 ASan/TSan/fuzz + 评审事后发现。**这是数量级的差别，不是风格偏好。**

### 2. 目标架构全部是 Tier 1

| 架构 | Rust target | Tier |
|---|---|---|
| x86_64 Linux | `x86_64-unknown-linux-gnu` | Tier 1（glibc 2.17+） |
| ARM64 Linux | `aarch64-unknown-linux-gnu` | Tier 1（glibc 2.17+） |
| x86_64 Windows | `x86_64-pc-windows-msvc` | Tier 1（Server 2016+） |

**没有一个目标需要自建工具链。**

### 3. 编译器与 OS 解耦

C++ 路线需要为各发行版的老编译器做兼容：

- 麒麟 V10 服务器只有 **GCC 7.3**（无 `std::filesystem`，无 gcc-toolset）
- 麒麟 V10 初版桌面是 **GCC 5.3.1**（默认不支持 C++17）
- libstdc++ 版本差异导致 `GLIBCXX_3.4.28 not found`

Rust 用 rustup 统一工具链，**std 静态链入，产物只依赖 glibc**。这直接消除了整类兼容问题。

### 4. 有成功的先例

- **Zenoh**（Rust 核心 + C ABI）
- **iceoryx2**（Rust 核心 + C/C++ 绑定）

两者都是 greenfield 独立项目，与本库定位一致。

### 5. 前一轮否决的理由已经消失

之前倾向 C++17，是因为「必须覆盖龙芯/申威」：

| 曾否决的理由 | 现状 |
|---|---|
| LoongArch 官方 std 要求 glibc 2.36 / 内核 5.19 | 不在范围 |
| MIPS64 Tier 3，无预编译 std | 不在范围 |
| SW64 无 LLVM 后端 | 不在范围 |
| 受 monorepo C++17 / CMake 3.10 约束 | 独立库，不受约束 |

## 代价与缓解

| 代价 | 缓解 |
|---|---|
| FFI 边界本身仍是 UAF 高发区 | C ABI 契约 + 代际句柄 + 跨语言一致性测试（C/C++ 各编一遍头） |
| `cxx` 的 panic→abort 会杀宿主 | **不用 `cxx`**；裸 `extern "C"` + `catch_unwind` → 错误码 |
| tokio 会强加运行时 | **核心用 `mio` + 自研事件循环**；tokio **不进入任何 crate 的依赖**（至多出现在基准/示例，不进产物） |
| 团队学习曲线 | 先做最小纵向切片（TCP echo + 句柄表 + 发现）验证 |
| 供应链 | 核心只依赖少数成熟 crate（`mio`、`socket2`，见架构 §2 crate 依赖表），vendor 锁定 |
| 调试体验 | Windows 用 MSVC target（CodeView/PDB）；Linux 用 GDB/LLDB |

---

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **C++17/C++23 核心** | 各发行版老编译器带来兼容负担；安全靠纪律而非编译期保证。若团队是纯 C++ 且短期内不引第二套工具链，仍是**对等的务实备选** |
| **C 核心 + C++ 门面** | 行业统一的是 C **公开 ABI**，不是 C 核心（ZeroMQ/Fast DDS/iceoryx 都是 C++ 核心 + C API）；C 核心不会让实现更安全，还丢掉 RAII 与基础设施复用 |
| **Go 核心** | 运行时拥有线程与调度器，与「调用方驱动事件循环」冲突；`c-shared` 不可安全卸载 |
| **C# / Java 核心** | 运行时/GC/部署形态不适合可嵌入的 IO 核心 |
| **Zig 核心** | 语言未 1.0；生态与 Windows 支持不足；不适合长期基础设施 |
| **直接用 nng / ZeroMQ 作底座** | 句柄注册 / 发现 / 监控三块**它们都不提供**，横竖要自研；且引入 C 依赖与（nng 2.0 刚发布的）版本风险 |
| **Cyclone DDS 单依赖** | 功能覆盖好，但与「不含数据格式」冲突，且概念负担重 |

---

## 后果

### 正面

- 异步/并发/生命周期缺陷由编译器拦截。
- 一套工具链覆盖全部目标 OS，不受发行版编译器版本牵制。
- 交叉编译到 ARM64 成熟。
- 对外的 C ABI 使任何语言都能消费。

### 负面

- 引入第二套工具链（rustup / cargo）。
- 团队需要 Rust 能力。
- 二进制体积会比等价 C++ 实现略大（待实测）。

### 构建配置的硬要求

| 配置 | 要求 | 理由 |
|---|---|---|
| **`panic = "unwind"`** | **必须**（不能 `abort`） | C ABI 入口依赖 `catch_unwind` 把 panic 转成错误码；`panic=abort` 会使该承诺失效，一个 Rust bug 直接杀宿主 |
| `cdylib` / `staticlib` | 两者都产出 | 前者供动态加载，后者供静态链接 |
| `opt-level` | Release 用 3，调试构建保留符号 | 现场崩溃需可符号化 |

### 需要持续关注

- 依赖树膨胀 → 用 `cargo-deny` 审计 advisories/licenses/sources。
- `mio` 在各目标架构上的行为 → CI 覆盖 x86_64 与 aarch64。
- LoongArch/SW64 的重新评估信号 → 见 [平台支持 §5](../platform-support.md)。
